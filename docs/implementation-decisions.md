# Initial implementation decisions

Preflight 00, reviewed 2026-10-03. This records the initial contracts and dependency choices for the authorized preflight task. It does not implement prompts 01-03 or approve deployment, paid provider calls, or releases. The [server specification](shift-server-v0.md) owns execution semantics; the [client specification](shift-client-v0.md) owns desktop behavior. Later prompts must preserve those semantics when a library proves incompatible.

## Repository evidence and decision status

The worktree was clean before preflight. `apps/server` and `apps/app` contain manifests and README files only. There are no reusable components, application dependencies, source files, build scripts, tests, or CI jobs. The root pins `pnpm@12.6.0` and requires Node `>=24 <25`; the lockfile has empty application importers. Observed tools are Node 24.19.0 and pnpm 12.6.0 on Linux x64, glibc 2.39.

Keep exactly these two application workspaces. Server domain, protocol, store, engine, harness, integration, testing, and CLI modules belong inside `apps/server`. Main, preload, client-core, and client-ui belong inside `apps/app`. Server section 15 and `prompts/COMMON.md` explicitly override the expanded layout and M01's reference to domain/protocol packages. No `packages/protocol`, desktop rename, separate CLI workspace, or extra testing workspace is needed.

“Select now” freezes an implementation approach. Exact dependency pins enter manifests only in the prompt that uses them, after its build checks. “Verify later” names a bounded evidence gate, not permission to change product behavior. Publication dates below come from the npm registry's version records retrieved on 2026-10-03. They show release activity, not a support or security guarantee. Moving documentation links must be rechecked against the version actually installed.

## Durable workflow and job review

Shift needs one process and one authoritative SQLite database. A transition must commit state, events, receipts, and jobs together. Human waits may have no deadline and must consume no worker slot. Definitions are editable data with immutable published versions and run snapshots. External operations need persisted intent, fences, and an explicit unknown outcome that prevents blind replay. A library that provides durable waiting still needs to satisfy the transaction and effect rules.

The alternatives and their concrete recovery differences are recorded below. Product fit assessments are our inference from the cited APIs, rather than claims that these libraries cannot implement workflows in general.

Select a Shift-owned domain engine/store. This is necessary for single-path routing, predecessor-chain references, execution/attempt/invocation identity, immutable snapshots, holds, and action-specific reconciliation. Reuse SQLite, validation, cron, process, and stream libraries for their respective mechanisms. Do not write SQL storage engines, JSON Schema validators, cron parsers, subprocess buffering, or SSE parsers from scratch.

For `durable_jobs`, the initial recommendation is a small repository over the specification's table, sharing the same connection and synchronous transaction as state/events/receipts. Jobs point to domain records; they do not carry a second execution graph. Claims check generation and fence; stale completion cannot schedule a successor. Waiting is a persisted identifier/deadline, with no in-memory promise needed to resume it. Recovery inspects prior claims and effects before making work eligible. Unknown effects remain unavailable for ordinary retries.

This recommendation is narrower than “build all durable infrastructure ourselves.” Queuert demonstrates that transactional SQLite job reuse is possible. Its documented reaper changes an expired running job to pending and notifies retry. Worker backoff controls timing but does not document a processor retry-disable/max-attempts policy or an effect-classification hook before that reaper transition. Middleware could inspect Shift's journal before I/O; whether it can preserve a held unknown outcome and truthful attempt accounting remains unverified. [Worker design](https://kvet.github.io/queuert/advanced/in-process-worker/), [worker API](https://kvet.github.io/queuert/reference/queuert/worker/), [job processing](https://kvet.github.io/queuert/advanced/job-processing/).

Before prompt 05 implements jobs, recheck its pinned adapter/API and run a small adoption probe. Adoption must demonstrate, in a real database and subprocess crash test:

1. Domain state, event, receipt, and successor job share one commit and roll back together.
2. A leased job's recovery cannot bypass Shift reconciliation or consume an extra physical attempt invisibly.
3. An unknown external effect cannot be resubmitted by stage/lease retries; an old claim cannot complete under a new fence.
4. Human completion can commit through the command transaction after an indefinite wait, without a live worker or a second state authority.
5. Library migrations and retained chain history can coexist with Shift's schema, backup, and immutable audit requirements.

If those checks pass, prefer reuse of the job mechanism behind a repository interface. Otherwise retain the custom table/claim code and record the failed case. No assessed general workflow library currently demonstrates the entire required contract without another execution authority. That is evidence for the current recommendation, not a proof that no future library can fit. Prompts 05-09 and 19 must still prove Shift's own crash behavior.

## Protocol ownership and build-time consumption

Select server-owned JSON Schema 2020-12 files under `apps/server/src/protocol/schemas`. Protocol files contain data and public types only. Do not import executor registrations to produce catalog descriptions. Keep public catalog definitions separate from their server executor wiring. Contract fixture inputs belong under `apps/server/test/fixtures/protocol`; app-specific connection/rendering scenarios belong under `apps/app/test/fixtures` and must satisfy the same schemas.

Prompt 01 creates a generation tool under `apps/server/tools` that reads only an explicit schema/fixture allowlist, generates TypeScript declarations and Ajv standalone ESM validators, and emits a manifest with schema hashes and generator versions. Prompt 02 consumes a checked-in, deterministic copy in `apps/app/src/protocol/generated`, including approved fixture/catalog JSON. The server uses the same canonical schemas and validation options. Generated outputs must never import server source or a server package barrel. The app has no runtime or workspace dependency on `@shift/server`.

Generation is a development/build step, not server startup. Root `protocol:generate` and `protocol:check` scripts, to be added by 01, regenerate into a temporary output directory and compare against the committed app artifacts. Root CI runs this check before either build. App builds/typechecks work from the committed artifacts without loading the server/native binding. The generator is allowed to use Node filesystem APIs; its emitted code is limited to pure JS/types/JSON and explicitly bundled pure Ajv runtime helpers. Size/error diagnostic helpers need browser-compatible implementations.

Reject app source imports into `apps/server`, `@shift/server`, persistence, harnesses, executors, native addons, and server configuration. Validate the emitted dependency graph rather than trusting tree shaking: 02 adds a build/bundle check for forbidden imports/assets in all desktop entries, with renderer additionally excluding Electron and Node APIs. Never emit source maps containing backend source or test credentials. A pure output is not automatically a safe public payload; fixtures and schemas need a secret-field review too.

Use these initial families. Version numbers describe the family independently of database migrations, application release and executor implementation version.
